Как обновлять сайт в будущем
После пуша изменений в GitHub:
cd /var/www/onestep && git pull && npm ci && npm run build && pm2 reload onestep

Как обновлять сайт
После пуша изменений в GitHub — просто:

ssh root@xxx.21.60.3
cd /var/www/onestep && ./deploy.sh
Скрипт сам всё сделает по порядку. Если в git нет новых коммитов — он сделает бэкап и выйдет, ничего не ломая. Если сборка упадёт — автоматически откатит код и БД на рабочую версию. Весь ход пишется в /var/www/onestep/deploy.log.

⚠️ Важно про твой рабочий процесс с БД: изменения схемы должны приезжать готовыми миграциями в git. То есть локально: правишь schema.prisma → npm run migration:create → применяешь локально → коммитишь папку миграции → пушишь. На сервере deploy.sh их накатит через migrate deploy. Не запускай на сервере prisma migrate dev — он для разработки и может пересоздать базу.

Как восстановить БД из бэкапа
Посмотреть список бэкапов:


cd /var/www/onestep && ./restore.sh
Восстановить самый свежий:


./restore.sh latest
Восстановить конкретный (имя из списка):


./restore.sh dev.db.20260707-150914
Скрипт перед заменой сам сохранит текущую базу в backups/dev.db.before-restore-<время> — так что даже ошибочное восстановление можно отменить, накатив этот файл обратно тем же ./restore.sh.

Детали
Бэкапы: /var/www/onestep/backups/, имя dev.db.<дата>-<время>. Хранятся последние 10, старые удаляются автоматически.
Ручной бэкап в любой момент без деплоя:

sqlite3 /var/www/onestep/prisma/dev.db ".backup '/var/www/onestep/backups/dev.db.manual-$(date +%Y%m%d-%H%M%S)'"
Скрипты лежат рядом с проектом и не в git (untracked) — обновлениям через git pull не мешают.

Как забрать боевую базу к себе на локальную машину
Скрипт scripts/pull-prod-db.sh (он в git, приезжает вместе с кодом).

⚠️ Запускать ТОЛЬКО со своей машины, не с сервера. Скрипт сам подключается на прод по SSH. Если запустить его на сервере, он подменит боевую базу её же снимком и удалит журнал у живой базы. На такой случай в скрипте стоит предохранитель: увидев локальный каталог /var/www/onestep, он откажется работать.

Из Git Bash в корне проекта:

cd /c/Users/vitalii/Documents/Projects/onestep
bash scripts/pull-prod-db.sh                 # только база
bash scripts/pull-prod-db.sh --with-uploads  # база + вложения CRM

Другой адрес сервера — через переменную: SERVER=root@1.2.3.4 bash scripts/pull-prod-db.sh

Что он делает по шагам:
1. На сервере снимает консистентный снимок через sqlite3 .backup во временный /tmp (простой cp/scp с живой базы может приехать битым — снимок обязателен) и после скачивания удаляет его.
2. Качает снимок в prisma/dev.db.prod-<время> — промежуточный файл, чтобы оборванная закачка не убила рабочую базу.
3. Текущую локальную базу откладывает в prisma/dev.db.bak-local-<время> — это откат: скопировать файл обратно в prisma/dev.db.
4. Кладёт скачанное в prisma/dev.db и чистит хвосты журнала (-wal, -shm, -journal) от прежней локальной базы.
5. С флагом --with-uploads тянет rsync-ом /var/www/onestep/uploads/ в локальный uploads/ (если rsync в Git Bash нет — scp -r root@83.217.202.170:/var/www/onestep/uploads/. uploads/).
6. Показывает npx prisma migrate status.

Вложения живут отдельно от базы, в /var/www/onestep/uploads/ — в базе хранятся только ключи файлов. Без папки uploads вложения в локальной CRM будут отдавать 404.

Локальный .env не трогается — NEXTAUTH_URL остаётся localhost. Но вместе с базой приедут боевые пользователи и их пароли: логиниться локально придётся боевой учёткой, локальный BOOTSTRAP_ADMIN больше не подойдёт.

Если migrate status покажет непримененные миграции — значит в git есть миграции новее прода. Накатите локально: npx prisma migrate deploy
